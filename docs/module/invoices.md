# Modul: Invoice & Pembayaran

> Modul inti untuk menagih klien: membuat invoice berisi item layanan (dengan HPP/COGS dan titipan pajak) — atau, untuk perusahaan bertemplate Debit Note (PT SLU, PT BAS, PT MKB, PT BCB, PT AOE), **Debit Note** yang menagih kembali talangan atau menagih jasa —, mengirimkannya (penomoran resmi), mencatat pembayaran ke rekening bank, serta mengekspor rekap (Excel/PDF) dan mencetak invoice per-lembar (PDF klasik maupun template builder). Route prefix: `/invoices` (CRUD + export), `/payments` (update/hapus pembayaran), `/invoice/{invoice}/download|preview` (PDF), `POST /invoices/preview` (PDF pratinjau editor dari data belum tersimpan). Semua route digate permission Spatie: `view invoices` (grup), plus `create invoices`, `edit invoices`, `delete invoices` per aksi; `send` dan `rollback` ikut digate `edit invoices` (lihat `routes/web.php` baris 133–203).

## Fitur

### Daftar Invoice (Index + Statistik)
**Alur step-by-step:**
1. User membuka `/invoices` (GET, `can:view invoices`). Query string: `search`, `status` (`draft|sent|partially_paid|paid|overdue`), `client_ids[]`, `month` (default bulan berjalan `Y-m`), `date_from`/`date_to`, `per_page`, `sort`, `direction`.
2. `InvoiceController::index()` membangun query dengan join `clients` + subquery jumlah `payments` per invoice, memfilter periode via `applyPeriodFilter()` (range tanggal **menimpa** filter bulan bila salah satu bound terisi).
3. Kartu statistik mengikuti **semua** filter aktif termasuk tab status (sejak QA 2026-09-21; sebelumnya status diabaikan dan angka kartu terasa "tidak sesuai filter"). Hanya **hitungan per tab** yang mengabaikan status agar tab lain tidak membaca 0. Revenue/HPP/laba **mengecualikan `draft` dan `cancelled`**; `total_cogs` mengecualikan item `is_tax_deposit`; `total_tax_deposit` = Σ item titipan (titipan pajak + talangan Debit Note); `gross_profit` = ditagih + potongan PPh 23 − PPN − titipan − HPP (sejak 2026-11-18; sebelumnya titipan ikut terhitung laba); outstanding = billed − paid pada invoice `sent`/`partially_paid`.
4. **"Perlu ditagih"** (`status=overdue`) bukan status tersimpan: `applyStatusFilter()` memilih `sent`/`partially_paid` dengan `due_date < today` dan **mengabaikan filter periode** (lintas bulan), tetap ikut klien/pencarian. `stats.overdue_count` & `stats.overdue_amount` (Σ sisa tagihan) selalu dihitung lintas bulan, tidak terpengaruh tab.
5. Tanggal di baris daftar dikirim sebagai `Y-m-d` (bukan ISO UTC) — zona waktu app `Asia/Makassar` membuat ISO UTC mundur sehari di browser (QA 2026-09-26, BUG-02).
6. Respons: `Inertia::render('invoices/index', ...)` dengan props `invoices` (paginated), `stats`, `clients`, `customTemplates` (daftar `PdfTemplate` builder), `selectedInvoiceId`, `filters`.
7. Baris daftar membawa `document_type`; Debit Note diberi penanda bergaris tepi **Debit Note** di bawah nomornya (`DebitNoteChip` di `components/ob.tsx`, gaya penanda Pendanaan — bukan pil status).
8. UI (gaya Obsidian): kartu ringkasan (total ditagih, **PPN** — hanya bila `ppnEnabled` (perusahaan PKP) atau `stats.total_ppn > 0`, berisi Σ `ppn_amount` + `stats.ppn_invoice_count` invoice terbit ber-PPN di filter aktif —, sudah dibayar, belum dibayar, perlu ditagih + bar sebaran status; 4 atau 5 kolom, ukuran angka mengikuti lebar baris lewat container query `--stat-cols`/`--stat-pad`), pil status + pil "Perlu ditagih", tabel. Klik baris → drawer detail (lihat berikut).

Kelayakan rollback dihitung per invoice di `data()` (`rollbackable` = status `sent` dan `Invoice::isInvoiceLatestInMonth()`), sama dengan aturan yang ditegakkan `rollback()`.

### Detail Invoice (modal global `#invoice/{id}`)
Detail invoice adalah **modal yang menumpang di halaman mana pun**, seperti Settings di claude.ai: halaman di belakang tidak berganti, URL hanya ditambah hash. Contoh: dari Ringkasan → `/dashboard#invoice/13`; dari daftar → `/invoices?month=2026-09#invoice/13`.

**Alur step-by-step:**
1. Tautan detail adalah anchor biasa ke `#invoice/{id}` (`resourceHref()`), atau `openResource('invoice', id)` dari kode (klik baris daftar, notifikasi). Tidak ada permintaan ke server untuk halaman di belakang.
2. `lib/resource-modal.ts::installResourceModal()` (dipasang di `inertia.tsx` **sebelum** `createInertiaApp`) mencegat `popstate` yang hanya mengubah hash: Inertia tidak menangani (tidak menggulir ke atas / memasang ulang halaman), lalu `router.replace` sisi klien menyamakan URL & state riwayat Inertia.
3. `ResourceModalHost` (`components/resource-modal-host.tsx`, dirender `AppLayout`) membaca **`window.location.hash`** lewat `useResource()` — bukan `usePage().url`, karena saat halaman dimuat ulang Inertia menempelkan hash ke objek halamannya tanpa memicu render ulang — dan me-render `InvoiceDrawer` (dimuat malas).
4. Drawer mengambil `GET /invoices/{id}/data` (JSON: header + `amount_paid`/`amount_remaining`, `tax_deposit_total` (Σ item titipan pajak, untuk pratinjau jurnal pembayaran), klien, `items` (+ `client_name`), `payments` (+ `created_at`), `next_invoice_number` untuk draft, `rollbackable`, `custom_templates`, `created_at`/`updated_at`) — mandiri, tidak butuh props halaman invoice. 404 → "Invoice tidak ditemukan", halaman di belakang tetap.
5. Aksi di drawer (kirim, rollback, hapus, bayar) memakai **fetch JSON** (`send`/`rollback`/`destroy` menjawab JSON bila `expectsJson()`, lewat `actionResult()`), bukan kunjungan Inertia yang akan mengganti halaman di belakang. Setelah berhasil drawer memuat ulang datanya dan host memanggil `router.reload()` — URL sama sehingga Inertia mempertahankan hash dan modal tetap terbuka, sementara angka di halaman belakang ikut segar.
6. Tutup: bila modal dibuka dari dalam aplikasi → `history.back()`; bila datang dari tautan/refresh → `router.replace` ke URL tanpa hash. Back/Forward browser menutup/membuka ulang modal; refresh dan tautan yang dibagikan (tombol salin tautan menyalin `location.href`) membuka halaman yang sama dengan modal terbuka.
7. Rute lama `GET /invoices/{id}` (`show()`, notifikasi lama, redirect setelah simpan) tetap merender daftar dengan `selectedInvoiceId`; halaman daftar langsung mengubahnya menjadi `/invoices#invoice/{id}` (`showResource()`). Notifikasi jatuh tempo baru memakai `/invoices#invoice/{id}` dan membuka modal di halaman yang sedang dibuka.
8. Isi drawer: metrik (total, dibayar, sisa, laba kotor — Debit Note talangan: **Talangan** "diganti klien · bukan pendapatan"; Debit Note tagihan jasa sama dengan invoice), penanda **Debit Note** di samping nomor, tab **Ringkasan** (item, total, riwayat dari `created_at` + pembayaran, kartu klien, daftar pembayaran ubah/hapus) dan **Pratinjau cetak** (PDF asli via `/invoice/{id}/preview`). Aksi: Cetak, Terbitkan invoice (draft), Catat pembayaran (sent/partial), menu Ubah / Kembalikan ke draft / Hapus, salin tautan.

### Buat Invoice (Create + Store)
**Alur step-by-step:**
1. User klik "Buat Invoice" → GET `/invoices/create` (`can:create invoices`). Props dari `formOptions()`: klien `Active` (id, name, email, npwp, type) dan `services`. Editor (`InvoiceEditor` di `create.tsx`, dipakai juga `edit.tsx`): kiri isian, kanan **pratinjau PDF langsung**. Klien yang belum ada bisa dibuat tanpa meninggalkan editor: baris **+ Buat klien baru** di akhir pemilih Klien membuka modal **Klien baru** (lihat [clients.md › Tambah Klien](clients.md#tambah-klien-store)); klien tersimpan langsung terpilih.
2. User memilih klien, tanggal, dan **termin** (isian "Termin (hari)" di samping Jatuh tempo; jatuh tempo = tanggal invoice + termin, saling mengikuti: ubah termin → tanggal bergeser, ganti tanggal invoice → jatuh tempo ikut bergeser dengan termin yang sama, pilih tanggal manual → termin menyesuaikan; nilai awal = `company_profiles.default_due_days`, prop `defaultDueDays` dari `formOptions()`). Di form **invoice baru**, pemegang `manage invoice settings` melihat tombol "Jadikan N hari bawaan" bila termin berbeda dari bawaan → `PUT /settings/invoice-numbering/due-days` (`InvoiceSettingsController::updateDueDays`, 0–365 hari, partial reload `defaultDueDays`) — tanpa membuka halaman Pengaturan. Lalu user menyusun item (nama layanan dengan saran katalog saat mengetik, atau tombol katalog 🔍 di setiap baris yang mengisi nama & harga baris itu saja, qty, harga, satuan, **HPP** = HPP seluruh baris, sakelar titipan pajak). Tata letak baris item mengikuti **lebar kartu Item** (container query `@container`, bukan lebar layar, karena editor menyempit saat pratinjau terbuka; `ITEM_GRID`/`ITEM_AT` di `create.tsx`): ≥ `@2xl` tabel dua tingkat sejajar kepala kolom (layanan · qty · harga satuan · subtotal, di bawahnya opsi baris · satuan · HPP berprefiks "HPP" · hapus); `@md`–`@2xl` layanan selebar baris, lalu `qty · satuan × harga = subtotal`, lalu opsi · HPP · hapus; di bawah `@md` (ponsel) bertumpuk. Opsi baris = Tambah keterangan, Titipan pajak, klien per baris. Penempatan kolom memakai `col-[…]` (satu properti `grid-column`) agar tingkat yang lebih lebar menimpanya utuh. Lalu opsional "Tagih ke beberapa klien" (klien per baris), lalu kartu **Penyesuaian**: daftar baris seragam (judul + keterangan kiri, sakelar kanan, isian muncul di bawah saat menyala; `AdjustmentRow` di `create.tsx`) — **Beri diskon** (nominal/persen + alasan; mematikan sakelar mengosongkan diskon), bila perusahaan PKP **Tagih PPN x%** (bawaan menyala) + nomor faktur pajak (lihat "PPN"), dan bila dipakai **Dipotong PPh 23 oleh klien** + tarif (lihat "Potongan PPh 23"). Ringkasan angka (subtotal … Total, lalu Laba kotor & Est. PPh final) berada di kotak `bg-ob-inner`; kartu ini juga memakai container query: dua kolom (penyesuaian · ringkasan) hanya bila kartu ≥ `@3xl`, selain itu bertumpuk (mis. saat pratinjau terbuka). Ctrl+Enter menambah baris.
3. **Pratinjau langsung:** setiap isian berubah (jeda 350 ms, permintaan lama dibatalkan) editor mengirim `POST /invoices/preview` (`InvoicePreviewRequest`, semua field boleh kosong) → `preview()` membangun `Invoice` + `InvoiceItem` **tanpa menyimpan** (relasi di-`setRelation`), lalu `InvoicePrintService::renderPdf()` — jalur yang sama dengan unduhan — dan membalas **PDF**; nomor (tersimpan atau perkiraan `generateInvoiceNumber`) di header `X-Invoice-Number`. Parameter `highlight` (indeks baris yang sedang diedit) menyuntikkan CSS latar biru pada baris itu — hanya di pratinjau. Browser menampilkan PDF dengan penampil bawaan (`#toolbar=0&view=FitH`). Balasan **503** (database sedang restart, lihat Halaman error di [README](README.md)) dicoba lagi otomatis setelah `Retry-After`, paling banyak 12 kali berturut-turut; status lain tetap menunggu isian berubah atau tombol **Coba lagi**.
   **Harga satuan** Rupiah memakai `CurrencyInput decimals={2}`: boleh bersen, koma = desimal & titik = ribuan ("0,85", "9.459,46"); jumlah baris dibulatkan ke Rupiah (`lineAmount()`), sama dengan server. `StoreInvoiceRequest`/`InvoicePreviewRequest`: `numeric`, `min:0`, `max:9999999999999`, `decimal:0,2` ("Harga satuan baris 1 maksimal dua angka di belakang koma."). Drawer menampilkan harga satuan dengan sen (`rpSen()` di `components/ob.tsx`); PDF bawaan (Kisantra, Generik, Semesta), template perusahaan, dan kolom Harga Satuan template builder (`TemplateTokens::formatRupiah`) mencetak "9.459,46" lewat `InvoiceTotalRows::format()` (dua desimal hanya bila bersen); alat MCP `detail-invoice` mengembalikan `harga_satuan` bersen sebagai angka desimal. Invoice berulang, pengajuan dana, dan katalog layanan tetap Rupiah bulat.
4. Submit → POST `/invoices`, divalidasi `StoreInvoiceRequest` (pesan Indonesia di `messages()`, mis. "Nama layanan baris 1 wajib diisi."). Tombol **Simpan draft** atau **Simpan & terbitkan** (`publish=1`). **Simpan & terbitkan** lebih dulu membuka dialog **nomor invoice** (komponen bersama `components/invoice-number-dialog.tsx`, juga dipakai "Terbitkan invoice" di drawer): terisi `GET /invoices/next-number?client_id=&issue_date=` (`NextInvoiceNumberRequest` → `Invoice::generateInvoiceNumber()`, sama persis dengan nomor otomatis), bisa diubah oleh pemegang `edit invoices` (pengguna lain melihatnya read-only). Konfirmasi mengirim `publish=1` + `invoice_number`. Bila yang ditolak hanya nomornya (mis. "Nomor ini sudah dipakai invoice lain."), dialog tetap terbuka dengan tautan "Pakai nomor yang disarankan"; galat lain menutup dialog dan tampil di form. Tanpa klien/tanggal, tombol langsung mengirim agar validasi server menunjukkan yang kurang.
5. `store()` dalam `DB::transaction`: `buildInvoiceData()` (satu-satunya tempat hitungan: `amount = round(unit_price × quantity)`, `subtotal`, `discount_amount`, `ppn_rate`/`ppn_amount` lewat `resolvePpnRate()`, `total_amount = max(0, subtotal − discount) + ppn_amount`) → insert `draft` tanpa nomor + items; bila `publish`, `publish()` memberi nomor dari dialog (`invoice_number`, divalidasi `unique` di `StoreInvoiceRequest` — update mengabaikan dirinya; **dipakai hanya bila pengguna punya `edit invoices`**, selain itu diabaikan) atau `generateInvoiceNumber()` bila kosong, lalu status `sent` di transaksi yang sama.
6. Redirect ke **`invoices.show`** (drawer invoice baru terbuka) dengan flash `success`.

**Penjelasan kode** (`app/Http/Controllers/InvoiceController.php::store`):
```php
$discountAmount = $discountType === 'percentage'
    ? (int) round($subtotal * $discountValue / 100)
    : $discountValue;
$ppnRate = $this->resolvePpnRate($validated, $existing);
$ppnAmount = Invoice::ppnFor($subtotal - $taxDeposits - $discountAmount, $ppnRate);
'total_amount' => max(0, $subtotal - $discountAmount) + $ppnAmount,
```
Diskon persentase dikonversi ke nominal integer saat simpan (kedua bentuk disimpan: `discount_value` mentah + `discount_amount` hasil). Invoice selalu lahir sebagai `draft` tanpa nomor — nomor baru diberikan saat "send".

### Ubah Invoice (Edit + Update)
**Alur:** GET `/invoices/{invoice}/edit` (`can:edit invoices`) merender `invoices/edit` dengan data invoice + items; PUT `/invoices/{invoice}` divalidasi `UpdateInvoiceRequest` (identik dengan Store — `class UpdateInvoiceRequest extends StoreInvoiceRequest {}`). `update()` memakai `buildInvoiceData($validated, $invoice)` yang sama (invoice lama ikut dikirim agar tarif PPN tersimpannya dipakai), lalu **menghapus semua item lama dan membuat ulang** dalam satu transaksi. ### PPN (perusahaan PKP)
Sejak 2026-10-13. PPN dipilih **per invoice**, hanya selama Pengaturan › Profil perusahaan berstatus PKP dengan `ppn_rate > 0` (`formOptions()['ppn'] = {enabled, rate}`).

1. Editor menampilkan sakelar **Tagih PPN {rate}%** bila PKP aktif, atau bila invoice yang diedit sudah ber-PPN (tarif tersimpannya). Bawaan: invoice baru menyala bila PKP; invoice yang diedit mengikuti keadaannya (`apply_ppn = ppn_rate !== null`). Saat menyala muncul isian **No. faktur pajak (opsional)**; mematikan sakelar mengosongkan faktur.
2. Payload membawa `apply_ppn` (boolean, opsional) + `faktur` — divalidasi `StoreInvoiceRequest`/`InvoicePreviewRequest`.
3. `resolvePpnRate($validated, $existing)`: invoice yang sudah ber-PPN memakai **tarif tersimpannya** (tidak ikut bila tarif di Pengaturan diganti atau PKP dimatikan); invoice baru hanya bisa ber-PPN selama PKP; `apply_ppn` kosong = bawaan di atas; `apply_ppn=true` saat perusahaan tidak PKP diabaikan (PPN 0, bukan error). Invoice lama (`ppn_rate NULL`) yang diedit tanpa PPN tetap `NULL`.
4. **DPP = subtotal layanan − titipan pajak − diskon** (`Invoice::dpp_amount`); `ppn_amount = round(DPP × rate / 100)` (`Invoice::ppnFor()`, satu-satunya rumus — dipakai juga publish invoice berulang). PPN masuk `total_amount`, sehingga sisa tagihan, status Lunas, dan pembayaran memakai total **termasuk PPN**.
5. PPN **bukan pendapatan**: `gross_profit` model, laba kotor drawer/editor, statistik daftar (`gross_profit = total_revenue − total_ppn − HPP`; `stats.total_ppn` & `stats.ppn_invoice_count` tampil di kartu **PPN** daftar invoice), Ringkasan (`total_profit` dikurangi PPN yang sudah dibayar klien), rekap (omzet tanpa PPN), dan Laba Rugi (`ppn_output`, lihat `profit-loss.md`).
6. PDF: lihat "Download / Preview PDF Invoice".

### Potongan PPh 23 (dipotong klien)
Sejak 2026-11-18. Klien badan usaha memotong PPh 23 dari tagihan jasa dan menyetorkannya ke negara (bukti potong), sehingga yang ditransfer = DPP + PPN − PPh. **Hanya untuk perusahaan yang memakainya**, diatur seperti PKP di Pengaturan › Profil perusahaan (`company_profiles.pph_enabled` + `pph_rate` tarif bawaan, lihat `settings.md`); berlaku di semua template (PKP maupun tidak).

1. **Editor:** di bawah sakelar PPN, sakelar **Dipotong PPh 23 oleh klien** + isian **Tarif PPh 23** (persen, boleh pecahan: `2`, `0,5`) — **hanya tampil** bila `pph.enabled` atau invoice yang diedit sudah dipotong (`invoice.pph_rate > 0`), dan tidak untuk Debit Note talangan (`pphAvailable` di `create.tsx`; Debit Note tagihan jasa sama dengan invoice). Ringkasan menampilkan baris "PPh 23 dipotong klien x%" (−) dan Total = yang ditransfer klien.
2. **Bawaan** (`formOptions()['pph']` = `InvoiceController::pphOptions()`): `enabled`, `rate` = tarif bawaan Profil perusahaan, `clients` = `{klien: tarif}` dari invoice **terakhir** tiap klien yang punya keputusan PPh (`pph_rate` tidak null; 0 = tidak dipotong). Invoice baru di perusahaan yang memakai PPh 23: sakelar menyala dengan tarif bawaan; memilih klien mengikuti keputusan terakhir klien itu (`selectClient()` di `create.tsx`: 0 → mati, tarif → menyala dengan tarif itu). Mode edit tidak mengubahnya.
3. **Simpan** (`buildInvoiceData()` → `resolvePphRate()`): `apply_pph` + `pph_rate` (wajib bila dipotong, 0,01–100; `StoreInvoiceRequest`). Seperti `resolvePpnRate()`: perusahaan yang tidak memakai PPh 23 tidak bisa memotong invoice baru (`apply_pph` diabaikan, `pph_rate` null), invoice yang sudah dipotong tetap dengan tarifnya walau pengaturan dimatikan, dan `apply_pph` kosong = bawaan (invoice baru ikut pengaturan, invoice lama tetap). Tidak dipotong selama pengaturan menyala → `pph_rate = 0` (keputusan yang diingat). `pph_amount = round(DPP × tarif / 100)` (`Invoice::pphFor()`, satu-satunya rumus) dengan **DPP yang sama dengan PPN** (layanan − titipan − diskon). Debit Note talangan selalu tanpa PPh (`null`).
4. **Status & pembayaran:** karena `total_amount` sudah dikurangi PPh, transfer klien sebesar GRAND TOTAL langsung Lunas — tidak ada kode status/sisa/Perlu ditagih yang berubah.
5. **Bukan pengurang pendapatan:** potongan PPh 23 adalah kredit pajak perusahaan, jadi setiap angka laba/omzet menambahkannya kembali: `gross_profit` model, laba kotor drawer & editor, statistik daftar (`gross_profit = total_revenue + total_pph − total_ppn − titipan − HPP`; `stats.total_pph`), Ringkasan (`total_profit`), rekap (omzet = total + PPh − PPN − titipan), MCP `detail-invoice` (`pph23_tarif`, `pph23_dipotong_klien`).
6. **Laba Rugi & jurnal:** `Invoice::allocatePayments($paid, $titipan, $ppn, $pph, $total)` — setiap rupiah yang dibayar ikut melunasi bagian PPh-nya **secara proporsional** (`pph = round(pph × min(paid, total) / total)`), lalu "titipan dulu" berjalan atas `paid + pph`. Hasilnya saat lunas pendapatan = DPP penuh; memo Laba Rugi `pph_withheld` ("PPh 23 dipotong klien (kredit pajak, sudah termasuk pendapatan)"). Jurnal pembayaran mendebit **PPh 23 Dibayar di Muka** (`JournalService::PPH_PREPAID`) sebesar bagian itu, di samping Debit rekening; cermin klien di `resources/js/lib/journal.ts`.
7. **PDF:** template perusahaan lewat `InvoiceTotalRows` (baris `bruto` "Total Invoice + PPN (belum dipotong PPh)" bila ada PPN, lalu `pph` "PPh 23 (x%)" bernomor melanjutkan PPN; tanpa PPN: `dpp` "Total Invoice (belum dipotong PPh)"). SLU menulisnya "PPH" kapital seperti dokumen aslinya. Kisantra, Generik, dan Semesta menambah baris "PPH 23 x%" (−) sebelum TOTAL; terbilang = TOTAL. Template builder: token `{{invoice.pph_rate}}`, `{{invoice.pph_amount}}`.
8. **Belum:** invoice berulang (publish selalu tanpa PPh), jenis PPh lain (PPh 4(2) final, PPh 15, PPh 22) — semuanya dicatat sebagai PPh 23, dan rekap JSM (kolom "Total Invoice"/"Grand Total" tetap sebelum potongan).

Dikunci `tests/Feature/InvoicePphTest.php` dan `InvoiceTotalRowsTest`.

### Tagihan USD & kurs manual
Sejak 2026-11-20 (untuk BCB: klien luar negeri ditagih dalam USD; juga MKB/BCB invoice FINAL bertarif USD). **Pembukuan tetap Rupiah**: `total_amount`, item `amount`, `payments.amount` tetap Rupiah dan dibaca Laba Rugi, Kas & Bank, rekap, dan Ringkasan seperti biasa; USD hanya sisi tagihannya. Aktif per perusahaan lewat **Pengaturan › Profil perusahaan › Tagihan USD** (`company_profiles.foreign_currency_enabled`, bawaan mati); perusahaan lain tidak melihat apa pun.

1. **Editor** (`formOptions()['foreignCurrency'] = {enabled, lastRate}`; tampil bila sakelar menyala atau invoice ini sudah memakai kurs): **Mata uang tagihan** Rupiah/USD (`SegmentedControl`), **Kurs (Rp per 1 USD)** (`CurrencyInput`, terisi kurs terakhir) — tampil bila tagihan USD atau ada baris berharga USD —, dan per baris sakelar **Harga USD** (harga diisi `CurrencyInput prefix="USD" decimals={4}`, dengan keterangan "Harga USD × kurs … = Rp … per unit"). Ringkasan menambah **Tagihan USD (total ÷ kurs)**. Mata uang terkunci bila tagihan sudah menerima pembayaran (`resolveCurrency()`, `has_payments`).
2. **Simpan** (`buildInvoiceData()`): baris berharga USD → `amount = round(qty × harga USD × kurs)` (`Invoice::foreignLineAmount`, satu pembulatan di akhir: 55.070 × $0,75 × 17.898 = **739.232.145**, sama dengan Excel invoice FINAL 046 MKB), `unit_price` = harga USD × kurs dibulatkan ke sen. PPN, PPh, diskon, total tetap dihitung dalam Rupiah. Tagihan USD → `total_foreign = round(total ÷ kurs, 2)` (TKBM 097 BCB: 362.914.500 ÷ 18.218 = **$19.920,66**). Kurs disimpan bila dipakai. Validasi (`StoreInvoiceRequest::currencies()` / `foreignCurrencyAllowed()`): USD & harga USD ditolak bila sakelar mati (kecuali invoice yang sudah memakai kurs), kurs wajib untuk tagihan USD dan bila ada harga USD; batas diskon nominal memakai Rupiah baris USD.
3. **Sisa & status**: `foreign_paid` (Σ `payments.foreign_amount`), `foreign_remaining` (tidak minus), `amount_remaining` = sisa USD × kurs invoice (0 bila USD lunas — Rupiah yang masuk bisa melebihi `total_amount` saat kurs naik). `updateStatus()` membandingkan USD. Daftar, rekap Excel/PDF, kartu "Perlu ditagih"/"Belum dibayar" (`Invoice::outstandingTotal()`, satu query `CASE currency`), dan alat MCP memakai rumus yang sama.
4. **Pembayaran**: `StorePaymentRequest` untuk tagihan USD mewajibkan `foreign_amount` (≤ sisa USD + pembayaran yang diubah) dan `exchange_rate`; `PaymentController::nominal()` menyimpan `amount = round(USD × kurs saat diterima)` ke rekening Rupiah yang dipilih (rekening USD tidak dicatat di Kas & Bank), dan `exceedsRemaining()` membandingkan USD. Kirim `amount` saja untuk tagihan USD = 422.

### Terbitkan Invoice (Send — penomoran resmi)
**Alur step-by-step:**
1. Di drawer invoice `draft`, user klik "Terbitkan invoice" → dialog **terisi otomatis** dengan `next_invoice_number` dari `/invoices/{id}/data` (dihitung server via `Invoice::generateInvoiceNumber($issue_date, $billed_to_id)` → `InvoiceNumberService::next()`, jadi inisial klien sama persis dengan backend); user masih boleh mengubahnya sebelum konfirmasi.
2. POST `/invoices/{invoice}/send` payload `{ invoice_number }`, divalidasi `SendInvoiceRequest` (`unique:invoices,invoice_number` kecuali dirinya; pesan "Nomor ini sudah dipakai invoice lain." + tautan "Pakai nomor yang disarankan" di UI).
3. `send()` menolak jika status bukan `draft` (flash `error`). Jika lolos: `$invoice->update(['invoice_number' => ..., 'status' => 'sent'])`; hook `saving` model mengisi `invoice_sequence` dari nomor itu.

**Penjelasan kode** (`app/Services/InvoiceNumberService.php` — satu-satunya tempat nomor disusun):

- `settings()` membaca `invoice_number_format`, `invoice_number_padding` (1–5, jumlah digit **minimum** `{NO}`; 1 = tanpa nol di depan; urutan tetap bertambah melewatinya), `invoice_number_reset` (`monthly`/`yearly`/`never`) dari `CompanyProfile::current()`, dengan default format lama bila belum diisi.
- `next($issueDate, $clientId, $kode = 'INV')` = `render()` pola dengan `nextSequence()` (MAX `invoice_sequence` dalam periode reset `issue_date` + 1 — **satu urutan untuk semua jenis dokumen**, invoice dan Debit Note). Pemanggil memakai `Invoice::generateInvoiceNumber($tanggal, $klien, $jenis, $kode)`. Token: `{NO}` (urutan, diberi nol sesuai padding), `{KODE}` (jenis + kode dokumen, `Invoice::numberCode()`: `INV`, `INV-FINAL`, `DN`, `DN-PNBP`; sejak 2026-11-18), `{PT}` (**singkatan** di Profil Perusahaan, `company_profiles.abbreviation`, milik tiap perusahaan; cadangan bila kosong: inisial nama perusahaan, lalu "SPI". Gerbang `EnsureCompanyProfileComplete` mewajibkan singkatan sebelum perusahaan dipakai, jadi cadangan tidak tercapai lewat web), `{KLIEN}` (**alias klien** bila diisi di data klien, selain itu inisial nama/nama perusahaan klien, lewati PT/CV/dst.; "XXX" bila tidak ada — `clientCode()`), `{BLN_ROMAWI}`, `{BLN}`, `{THN}`, `{THN2}`.
- `sequenceOf($number)` membangun regex dari pola aktif: `{NO}` → `(\d+)`, `{KODE}` → segmen huruf/angka bertanda hubung, token lain dicocokkan per jenis karakter (bukan nilainya) agar nomor tetap terbaca walau nama perusahaan/klien berubah. Dipakai hook `saving` model. `kodeOf($number)` mengembalikan segmen `{KODE}`-nya (`INV-FINAL`) — dipakai migrasi Debit Note SLU.
- `formatError($format, $reset)` — validasi pola (dipakai `UpdateInvoiceSettingsRequest`, dicerminkan di frontend): hanya token dikenal, `{NO}` tepat sekali, reset bulanan wajib memuat bulan + tahun, reset tahunan wajib memuat tahun (tanpa itu nomor periode berbeda akan bentrok).

Pengaturan pola ada di modul Settings (`/settings/invoice-numbering`, lihat `settings.md`). Default (format, 3 digit, reset bulanan) menghasilkan nomor yang persis sama dengan generator lama (`InvoiceNumberServiceTest::test_default_format_matches_the_company_numbering`).

### Rollback Invoice (Sent → Draft)
**Alur:** POST `/invoices/{invoice}/rollback` → `rollback()` menolak jika status bukan `sent`, dan menolak jika `Invoice::isLatestInNumberingPeriod($invoice)` false (hanya `invoice_sequence` **tertinggi** di periode reset `issue_date`-nya yang boleh, supaya tidak melubangi urutan nomor).

Untuk invoice ber-`invoice_sequence` null (nomor manual atau warisan yang tidak cocok pola) berlaku dua aturan berbeda, dan bedanya penting:
- Periode itu **masih punya** invoice bernomor urut → ekor deret adalah miliknya, nomor manual **tidak** bisa di-rollback (perilaku lama, dikunci `test_manual_number_outside_the_format_does_not_move_the_counter`).
- Periode itu **tidak punya satu pun** urutan (mis. seluruh riwayat memakai format lama) → yang **terakhir diterbitkan** dianggap ekornya. Tanpa cadangan ini seluruh riwayat terkunci selamanya: tidak bisa di-rollback, jadi tidak bisa dikoreksi. Dikunci `test_invoice_bernomor_warisan_tanpa_urutan_tidak_terkunci_selamanya`. Jika lolos: `invoice_number` di-null-kan (hook mengosongkan `invoice_sequence`) dan status kembali `draft`.

### Pembayaran — Catat (POST /invoices/{invoice}/payments)
**Alur step-by-step:**
1. Di drawer, user klik "Catat pembayaran" → dialog: `amount` (CurrencyInput + chip Sisa penuh / 50% / Nominal lain), `payment_date`, `bank_account_id` (wajib; `/api/bank-accounts`), `payment_method` (Transfer bank / Tunai — benar-benar dikirim, sebelumnya selalu `bank_transfer`), `reference_number`. Tagihan USD: `amount` diganti **Diterima (USD)** (`foreign_amount`, CurrencyInput `decimals={2}`) + **Kurs saat diterima** (`exchange_rate`, terisi kurs invoice) dan baris "Masuk ke rekening: Rp …"; chip menghitung dalam USD (lihat "Tagihan USD & kurs manual")., `attachment`. Di bawah Metode tampil **Jurnal · Pratinjau** (sejak 9 Nov 2026): Debit rekening tujuan (`journal_name` dari `/api/bank-accounts`) / Kredit dipecah "titipan dulu" — **Titipan Pajak Klien**, lalu **PPN Keluaran**, sisanya **Pendapatan dari Invoice** — dari `tax_deposit_total` & `ppn_amount` invoice dan pembayaran yang sudah ada sebelum tanggal ini (urut tanggal, id; pembayaran yang diubah tidak dihitung). Rumusnya cermin `JournalService::paymentLines()` / `Invoice::allocatePayments()` di `resources/js/lib/journal.ts`; jurnal tersimpan tampil di rincian pembayaran Arus Kas & Kas & Bank. Lihat [cash-flow.md › Jurnal tampilan](cash-flow.md#jurnal-tampilan-cara-a--debitkredit-dari-rekening--kategori).
2. Frontend submit via `fetch` multipart POST ke `/invoices/{invoice}/payments` (route ber-middleware `can:create invoices`), validasi `StorePaymentRequest`.
3. `PaymentController::store()` menolak (422 JSON) jika status invoice `draft` atau `paid`, dan **jika nominal melebihi sisa tagihan** (`exceedsRemaining()`: "Melebihi sisa tagihan Rp X. Catat kelebihan sebagai transaksi terpisah."; UI juga memblokir sebelum kirim). `update()` memakai aturan yang sama dengan nominal lama ikut dihitung sebagai sisa. Lampiran disimpan ke `storage/app/public/payments`.
4. Insert `payments`, lalu **`$invoice->updateStatus()`** menghitung ulang status dari total pembayaran.
5. Respons JSON payment terformat; drawer memuat ulang `/data` dan halaman di belakang `router.reload()` (hash dipertahankan).

**Penjelasan kode** (`app/Models/Invoice.php::updateStatus`):
```php
if ($amountPaid == 0) {
    $this->status = $this->invoice_number ? 'sent' : 'draft';
} elseif ($amountPaid >= $this->total_amount) {
    $this->status = 'paid';
} else {
    $this->status = 'partially_paid';
}
$this->save();
```
Status murni turunan dari `amount_paid` vs `total_amount` — tagihan USD: dari Σ `foreign_amount` vs `total_foreign` dalam sen (`Invoice::cents`), jadi lunas saat USD-nya lunas berapa pun Rupiah yang masuk. Bila **semua** pembayaran dihapus, invoice yang sudah ber-nomor kembali ke `sent` (bukan `draft`) — sebelumnya ia jatuh ke `draft` sambil tetap memegang nomor, yang membuat `isInvoiceLatestInMonth()` memblokir rollback invoice lain di bulan yang sama.

**Penjelasan kode** (`app/Services/CompanyInvoiceTemplate.php`):
- `view()` → `pdf.perusahaan.{slug}.invoice` bila view itu ada untuk `tenant()` aktif, selain itu `null`. Slug divalidasi `[a-z0-9-]` karena ikut menjadi path.

- `option()` → `{value: 'perusahaan', label: <nama perusahaan>}` atau `null`; dikirim sebagai prop `companyTemplate` (index, create/edit lewat `formOptions()`) dan `company_template` (`/invoices/{id}/data`). Dialog cetak & editor hanya menawarkan opsi ini bila ada.
- `viewFor($template)` dipakai `InvoicePrintService::renderPdf()`; `asset($file)` mengembalikan data URI berkas di folder perusahaan aktif (`$aset('logo.jpg')` di Blade; nama berkas dengan path ditolak).
- Font milik template ditaruh di `fonts/` folder perusahaan (SLU: Tinos Regular/Bold untuk semua teks + Carlito-Bold untuk judul; BAS: Tinos Regular/Bold untuk teks utama, Carlito-Bold untuk judul, Caladea Regular/Bold untuk alamat & kotak info; MKB & BCB: Tinos Regular/Bold untuk semua teks dokumen, Caladea Regular/Bold untuk kedua kotak info, Arimo Regular untuk alamat di kotak alamat — tanpa Carlito; AOE: seperti MKB ditambah Carlito-Bold untuk judul berkotak; NAI: Tinos Regular/Bold untuk nomor, perihal & alamat klien, Carlito Regular/Bold untuk judul, baris TO/ATTENTION/TERM PAYMENT, baris total, kedua kotak info & tanda tangan, Arimo Regular untuk tabel item — tanpa Caladea; Carlito-Regular dari `google/fonts` `ofl/carlito`, sumber yang sama dengan Carlito-Bold (identik per byte). Tinos = pengganti **Times New Roman**, Carlito = Calibri, Caladea = Cambria, Arimo = Arial, semuanya berukuran & berlebar huruf identik dengan aslinya; lisensi OFL/Apache 2.0 di sebelahnya). Times New Roman asli tidak boleh di-commit (lisensi Monotype, repo publik); sebelum 2026-11-18 teks memakai core font `times` DomPDF yang **tidak tertanam**, sehingga bentuk hurufnya bergantung pada penampil PDF. Tinggi baris DomPDF sebanding tinggi font (Tinos terukur 1,15 em, core `times` 0,9 em), jadi semua `line-height` teks Tinos = nilai lama × 0,783 (1,15 → 0,9) — tata letak terukur sama (≤ 1 px pada 300 dpi) dan dimuat `@font-face` dengan `CompanyInvoiceTemplate::path()`. Folder tiap perusahaan berdiri sendiri, jadi font yang sama disalin (git menyimpan isi yang identik sekali). Khusus template perusahaan, `renderPdf()` memberi DomPDF `chroot`/`fontDir`/`fontCache` dari `config/dompdf.php` + subsetting font: `setOptions()` tanpa config membuat chroot = folder paket vendor sehingga berkas font di `resources/` ditolak diam-diam (judul jatuh ke Helvetica). Dikunci `CompanyInvoiceTemplateTest` (PDF memuat `Carlito-Bold` & `Tinos-Regular`/`Tinos-Bold`; BAS juga `Caladea-Regular`/`Caladea-Bold`) dan `TemplateInvoiceMkbTest`/`TemplateInvoiceBcbTest` (MKB & BCB: Tinos, Caladea, `Arimo-Regular`, tanpa Carlito) serta `TemplateInvoiceAoeTest` (AOE: keempatnya) dan `TemplateInvoiceNaiTest` (NAI: Tinos, Carlito Regular/Bold, Arimo).
- Tinggi baris DomPDF = `line-height` × (ascender − descender font) × `font_height_ratio` 1,1 (`config/dompdf.php`), bukan `line-height` × ukuran huruf seperti di browser. Untuk meniru spasi tunggal Word, `line-height` disesuaikan per font (Times 1,15; Caladea 0,91) — lihat komentar di Blade BAS. Terukur pada `line-height: 1`: Tinos 1,264 em, Caladea 1,289 em, Arimo 1,265 em, sehingga template MKB, BCB & AOE memakai 0,91 untuk ketiganya (= spasi tunggal Word ±1,15 em). Carlito (Calibri, 1,2207 em) juga 0,91, sehingga template NAI memakai 0,91 untuk semua font. DomPDF menghitung `width`/`height` sel tabel **tanpa** padding meski `box-sizing: border-box`, jadi ukuran kotak di Blade MKB, BCB & AOE = ukuran kotak Word dikurangi padding.

Service juga memisahkan `regular_items` vs `tax_deposit_items`, menghitung `terbilang` (angka → kata bahasa Indonesia via `numberToWords()`), dan menyematkan logo/ttd/stempel sebagai base64. `BuilderInvoicePrinter` (`app/Services/BuilderInvoicePrinter.php`) me-render layout JSON `PdfTemplate` (banded atau flat legacy) dengan `paymentContext` mode `full|dp|pelunasan` dan custom font.

## Perhitungan Accessor (app/Models/Invoice.php)

| Accessor | Rumus |
|---|---|
| `amount_paid` | Σ `payments.amount` (pakai relasi yang sudah loaded bila ada) |
| `amount_remaining` | `total_amount − amount_paid`; tagihan USD: `round(foreign_remaining × exchange_rate)` (0 bila USD lunas) |
| `foreign_paid` / `foreign_remaining` | tagihan USD: Σ `payments.foreign_amount` / `max(0, total_foreign − foreign_paid)` dalam sen; `foreign_remaining` null untuk tagihan Rupiah |
| `isForeign()`, `cents()`, `foreignLineAmount()`, `foreignTotalFor()`, `settledAtInvoiceRate()`, `outstandingTotal()` | tagihan USD: mata uang ≠ IDR; nominal USD → sen; Rupiah baris berharga USD; utang USD = total ÷ kurs; Rupiah yang tertutup USD yang diterima dengan kurs invoice (dasar alokasi Laba Rugi & jurnal); Σ sisa tagihan sekumpulan invoice dalam satu query |
| `total_cogs` | Σ `items.cogs_amount` (catatan: **termasuk** item titipan pajak; stats index mengecualikannya via query terpisah) |
| `gross_profit` | `total_amount + pph_amount − ppn_amount − Σ item titipan − total_cogs` (PPN dan titipan pajak/talangan bukan laba; titipan sejak 2026-11-18; potongan PPh 23 tetap laba, sejak 2026-11-18) |
| `taxDepositTotal()` | Σ `amount` item `is_tax_deposit` (titipan pajak klien / talangan Debit Note) |
| `dpp_amount` | `max(0, subtotal − Σ item titipan pajak − discount_amount)` — dasar PPN |
| `pphFor($dpp, $rate)` (statis) | Potongan PPh 23 = `round(DPP × tarif / 100)` — satu-satunya rumus |
| `allocatePayments($paid, $taxDeposit, $ppn, $pph = 0, $total = 0)` (statis) | "Titipan dulu": `{tax_deposit, ppn, revenue, pph}` dari jumlah yang sudah dibayar; `pph` = bagian potongan PPh 23 yang ikut lunas (proporsional terhadap `total`), dan ketiga bagian pertama berjumlah `paid + pph` — satu rumus untuk Laba Rugi, Ringkasan, dan jurnal pembayaran |
| `outstanding_profit` / `paid_profit` | porsi laba yang belum/sudah "tertutup" pembayaran (model tutup-modal-dulu: pembayaran dianggap menutup HPP lebih dulu) |

## Keterkaitan Antar Modul
- **Bank Account:** setiap `Payment` ber-`bank_account_id`; saldo bank = `initial_balance + Σ payments + Σ tx credit − Σ tx debit` (accessor `getBalanceAttribute` di `app/Models/BankAccount.php`) — mencatat/menghapus pembayaran otomatis mengubah saldo tampilan tanpa menulis apa pun ke tabel bank.
- **Recurring Invoices:** `RecurringInvoice::publish()` membuat baris di `invoices` + `invoice_items` (lihat `docs/module/recurring-invoices.md`).
- **Clients:** `billed_to_id` dan `invoice_items.client_id`; menghapus klien meng-cascade hapus invoice & item-nya (override `Client::delete()`).
- **Services:** master harga saat menyusun item — hanya disalin (snapshot), tidak ada FK.
- **Cash Flow & Laporan Laba Rugi:** membaca `payments` (kas masuk) dan `cogs_amount`/`is_tax_deposit` untuk omzet/HPP. Jurnal tampilan pembayaran (Arus Kas, Kas & Bank, dialog Catat pembayaran) memecah setiap pembayaran dengan rumus "titipan dulu" yang sama dengan Laba Rugi (`Invoice::allocatePayments()`), sehingga Σ kredit "Pendapatan dari Invoice" dan "PPN Keluaran" pembayaran satu periode sama dengan angka Laba Rugi periode itu. HPP tidak dijurnal di pembayaran (tidak ada uang yang bergerak).
- **PDF Templates (Settings):** `PdfTemplate` + `CustomFont` dipakai `BuilderInvoicePrinter`; daftar template builder dikirim ke halaman index sebagai `customTemplates`.

## Invarian & Jebakan
- Semua nominal **integer rupiah penuh** — jangan pernah pakai float; `quantity` satu-satunya decimal. Pengecualian: harga satuan item `invoice_items.unit_price` (decimal 15,2, boleh bersen — tetapi `amount` dan semua nominal turunannya tetap integer, `round(qty × harga)` di server dan cermin `lineAmount()` editor; diuji sama untuk 200.004 kombinasi qty × harga) dan sisi USD tagihan USD (`total_foreign`, `foreign_unit_price`, `payments.foreign_amount`, kurs) berupa decimal; bandingkan USD dalam sen (`Invoice::cents`), jangan float langsung.
- **Tagihan USD: USD mengikat, Rupiah membukukan.** Status Lunas, sisa, dan batas pembayaran dari `total_foreign`; `total_amount` & `payments.amount` tetap Rupiah untuk semua laporan. Jangan menghitung ulang `total_foreign` dari Rupiah setelah disimpan, dan jangan mengizinkan ganti mata uang setelah ada pembayaran.
- Selisih kurs **bukan** pendapatan invoice: Laba Rugi mengalokasikan pembayaran USD dengan kurs invoice dan menaruh selisihnya di Pendapatan/Beban Lain; jurnal mencatatnya di akun Selisih Kurs. Dengan begitu Σ kredit "Pendapatan dari Invoice" tetap = `revenue.invoice`.
- Invoice `draft` tidak punya `invoice_number`; nomor hanya diberikan saat `send` (termasuk invoice hasil publish recurring), unik global, sequence reset sesuai pengaturan (default per bulan `issue_date`).
- **Urutan dibaca dari `invoice_sequence`, bukan dari teks nomor** — bentuk nomor bisa diganti kapan saja. Jangan menulis `invoice_sequence` manual kecuali sengaja; biarkan hook `saving` yang mengisinya. Mengganti pola tidak mengubah nomor yang sudah terbit.
- Rollback hanya untuk invoice `sent` dengan sequence **tertinggi** di periodenya (`isLatestInNumberingPeriod`) — jaga urutan nomor tanpa lubang.
- `updateStatus()` menghasilkan `sent` (ber-nomor, belum ada pembayaran) / `draft` (tanpa nomor) / `partially_paid` / `paid`. `overdue` dan `cancelled` ada di enum DB tetapi tidak ada transisi otomatis di kode saat ini (cancelled hanya dipakai sebagai filter pengecualian statistik/export).
- Invoice yang punya pembayaran **tidak bisa dihapus**; hapus pembayarannya dulu.
- `send`/`rollback` dan **memilih nomor sendiri** di dialog terbit butuh `edit invoices`. User `view`+`create` saja (role staff) tetap bisa **Simpan & terbitkan** saat membuat invoice (sesuai panduan pengguna), tetapi nomornya selalu otomatis: `invoice_number` dari request diabaikan.
- Pembayaran ditolak untuk invoice `draft` dan `paid` (`PaymentController::store`, HTTP 422).
- `update()` invoice **menghapus dan membuat ulang seluruh item** — ID `invoice_items` tidak stabil; jangan menyimpan referensi ke ID item.
- Statistik & export mengecualikan `draft` + `cancelled` dari omzet/HPP/laba dan **mengikuti tab status aktif** (hitungan tab tidak); item `is_tax_deposit` dikecualikan dari HPP di stats index tetapi accessor `total_cogs` model **tidak** mengecualikannya.
- Filter periode: backend memprioritaskan `date_from`/`date_to` atas `month`; UI menjaga keduanya saling eksklusif (pilih rentang → bulan dikosongkan, pilih bulan → rentang dikosongkan) supaya label tidak menyesatkan.
- Saldo bank dihitung dinamis — tidak ada kolom saldo yang perlu (atau boleh) di-update saat mencatat pembayaran.
- Endpoint payment & `/invoices/{id}/data` merespons **JSON**; `send`/`rollback`/`destroy` menjawab JSON untuk permintaan `expectsJson()` dan redirect + flash untuk yang lain. Jangan ubah aksi drawer menjadi kunjungan Inertia (`router.post`): redirect back mengganti halaman di belakang modal dan membuang hash.
- Modal detail ditentukan `location.hash` (`#invoice/{id}`), bukan path. Modul lain yang ingin detail ber-URL memakai `lib/resource-modal.ts` + `ResourceModalHost` yang sama.
- **Pratinjau = ekspor.** Pratinjau editor, tab Pratinjau cetak, dan dialog cetak menampilkan PDF dari `InvoicePrintService::renderPdf()`, bukan HTML tiruan. Render HTML di browser **tidak** identik dengan DomPDF (DomPDF mengabaikan `display:flex`, tinggi baris tabel berbeda — terukur ±9,7% piksel beda, QA 2026-09-26). `test_preview_pdf_is_identical_to_the_downloaded_pdf` mengunci kesamaan byte (kecuali stempel waktu & `/ID` acak). Satu-satunya pengecualian yang disengaja: sorotan baris `highlight` di pratinjau editor.
- **Template perusahaan menang.** Perusahaan yang punya folder `resources/views/pdf/perusahaan/{slug}/` hanya bisa mencetak dengan template itu (+ template builder miliknya); jangan menambah jalan pintas yang menerima template bawaan untuknya. Hitungan tetap di `buildInvoiceData()`/model dan baris total di `InvoiceTotalRows`, bukan di Blade perusahaan; data perusahaan (alamat, rekening, kota, penanda tangan) dari Profil perusahaan, bukan ditulis di Blade. Gambar tanda tangan/stempel asli tidak boleh di-commit (repo publik) — selalu lewat upload Profil perusahaan.
- `buildInvoiceData()` adalah satu-satunya tempat hitungan subtotal/diskon/total untuk store, update, dan pratinjau — jangan menduplikasi rumus. Rumus PPN hanya `Invoice::ppnFor()`.
- **Tarif PPN dibekukan per invoice.** Mengubah tarif atau mematikan PKP di Pengaturan tidak mengubah invoice yang sudah ber-PPN; hanya invoice baru yang tidak lagi diberi PPN. Jangan menghitung ulang PPN invoice lama dari `CompanyProfile`.
- `ppn_rate NULL` ≠ `0`: NULL = invoice sebelum fitur PPN (PDF/rekap JSM memakai perilaku lama), 0 = sengaja tanpa PPN. Jangan menormalkan NULL menjadi 0 lewat migrasi data.
- PPN ikut `total_amount` tetapi **tidak pernah** dihitung sebagai omzet/pendapatan/laba — kurangi `ppn_amount` di setiap angka laba/omzet baru. Begitu pula item titipan (`is_tax_deposit`: titipan pajak klien & talangan Debit Note).
- **Potongan PPh 23 kebalikannya:** `pph_amount` sudah dikurangkan dari `total_amount` (yang ditransfer klien) tetapi **tetap pendapatan** — tambahkan kembali `pph_amount` di setiap angka laba/omzet baru yang dihitung dari `total_amount`, dan teruskan `pph_amount` + `total_amount` ke `Invoice::allocatePayments()`. Angka tagihan (sisa, Lunas, Perlu ditagih) cukup memakai `total_amount`.
- **Debit Note talangan = semua item talangan.** `isPassThrough()` (Debit Note dengan `is_pass_through` bukan `false`) selalu berarti semua item `is_tax_deposit`, HPP 0, tanpa PPN/PPh/faktur — ditegakkan di `buildInvoiceData()`; jangan membuat Debit Note lewat jalur lain tanpa aturan itu. Debit Note tagihan jasa tidak punya aturan khusus: semua hitungan, laporan, dan jurnal memperlakukannya sebagai invoice. Jangan memakai `isDebitNote()` untuk keputusan akuntansi (talangan, akun jurnal, PPN) — pakai `isPassThrough()`; `isDebitNote()` hanya untuk judul, nomor, dan template. Jenis & kode tidak berubah setelah nomor terbit; sifat boleh.
